# DOM Events: Propagation, Delegation, and Default Behavior

## Purpose

This project models DOM event behavior through five independent implementations:

| File | Engineering perspective | Main focus |
|---|---|---|
| Python | Explicit event-dispatch simulator | Event paths, phases, listeners, delegation, cancellation |
| JavaScript | Event-driven asynchronous model | Listener options, Promises, delegation, passive behavior |
| C++17 | Governance-style dispatch engine | Explicit ownership, STL structures, propagation control |
| Java 17 | Enterprise domain model | Immutable configuration, policies, domain validation, state behavior |
| PostgreSQL | Relational event model | Event targets, listeners, deliveries, policies, reporting |

The implementations use the same conceptual domain but are not mechanical translations of one another.

The central relationship is:

`Event target → propagation path → listeners → event phase → propagation control → default behavior`

The model deliberately distinguishes event propagation from default behavior. Propagation determines which listeners can execute. Default behavior is evaluated after dispatch and can be cancelled with `preventDefault()` when the event is cancelable.

---

## DOM Event Model

A DOM event represents an occurrence associated with an event target, such as a button click, keyboard action, form interaction, or pointer event.

For a nested structure such as:

`document → application → list → row → button`

an event dispatched at `button` can travel through the hierarchy.

The propagation sequence is conceptually:

`document`
`↓ capture`
`application`
`↓ capture`
`list`
`↓ capture`
`row`
`↓ capture`
`button`
`target`
`↑ bubble`
`row`
`↑ bubble`
`list`
`↑ bubble`
`application`
`↑ bubble`
`document`

The important phases are:

| Phase | Direction | Typical purpose |
|---|---|---|
| Capturing | Root toward target | Intercept or prepare handling before the target |
| At target | Target itself | Handle the event at its source |
| Bubbling | Target toward root | Allow ancestors to react to descendant events |

Not every DOM event bubbles. The implementations explicitly model this distinction through a `bubbles` property.

---

## Event Listeners

An event listener associates an event type with a callback.

The model supports several listener attributes:

- event type
- capture mode
- one-time execution
- passive behavior
- optional delegation selector
- enabled state in the database representation

A listener registered with capture enabled participates while the event travels toward its target.

A normal listener participates during the target or bubbling stages.

The listener configuration is intentionally separate from the event itself. An event is a runtime occurrence, while a listener is a persistent rule describing how a target responds to an event.

---

## Capturing

Capturing is the first propagation phase.

For a target nested under several ancestors, the event travels from the root toward the target.

The Python implementation constructs the complete root-to-target path and executes capture listeners in order.

The JavaScript implementation uses the same conceptual path but performs listener execution asynchronously, allowing handlers to return Promises.

The C++ implementation uses shared ownership of nodes and explicitly traverses the vector representing the root-to-target path.

The Java implementation treats event targets as domain objects and performs the propagation through an explicit `EventPhase` enum.

The PostgreSQL implementation represents the resulting path through a recursive CTE rather than attempting to reproduce an in-memory callback system.

---

## Target Phase

The target phase is distinct from ancestor capture and bubbling.

At the target, capture listeners can execute first, followed by ordinary target listeners.

This distinction matters because a target may have both capture and non-capture listeners for the same event type.

The implementations preserve this ordering:

`target capture listeners → target bubble listeners`

A listener registered on an ancestor is not considered a target listener merely because it receives a bubbling event.

---

## Bubbling

Bubbling moves from the event target back toward the root.

For example:

`button → row → list → application → document`

This enables ancestor components to react to events generated by descendants.

Bubbling is especially useful when many dynamically created elements have the same behavior. Instead of installing one listener on every child, a parent can observe bubbled events.

The implementations explicitly disable this stage when `bubbles` is false.

This distinction is important for events whose semantics do not include ordinary bubbling.

---

## Event Delegation

Event delegation is a listener-management technique based on propagation.

A listener is placed on an ancestor, while the listener examines the event target or an ancestor of that target to determine whether the event should be handled.

Example model:

`table`
`└── row.user-row`
`    └── button`

A delegated listener on `table` with selector `.user-row` can handle events originating from a matching row.

Delegation differs from bubbling:

- Bubbling describes event propagation.
- Delegation describes how application code uses propagation to centralize handling.

The Python, JavaScript, C++, and Java implementations support selector-based delegated listeners.

The PostgreSQL representation stores delegated listeners with `listener_kind = 'delegated'` and a selector.

Delegation can reduce listener count for large dynamic interfaces, but the matching logic must remain precise. A broad selector can cause unrelated descendants to be processed.

---

## `stopPropagation()`

`stopPropagation()` prevents the event from continuing to other nodes in the propagation path.

It does not inherently mean that every listener on the current node stops executing.

The implementations therefore maintain two distinct states:

- propagation stopped
- immediate propagation stopped

This distinction prevents a common conceptual error.

A stopped propagation path can still contain multiple listeners on the current target.

---

## `stopImmediatePropagation()`

`stopImmediatePropagation()` is stronger.

It prevents:

1. execution of later listeners on the current target
2. continuation of propagation to other targets

The C++, Java, Python, and JavaScript models explicitly represent this as a separate state.

This distinction is important for security-sensitive or policy-sensitive handlers where later listeners must not execute after a decisive event handler has taken control.

---

## `preventDefault()`

`preventDefault()` does not stop event propagation.

It affects the event's default behavior.

The model therefore treats these operations separately:

`stopPropagation()`  
→ affects propagation

`stopImmediatePropagation()`  
→ affects propagation and remaining listeners on the current target

`preventDefault()`  
→ affects default behavior

For a cancelable event:

`listener executes → preventDefault() → dispatch completes → default action is skipped`

For a non-cancelable event, calling `preventDefault()` has no cancellation effect.

This distinction is one of the most important aspects of DOM event handling.

---

## Default Behavior

An event can have behavior associated with it beyond listener execution.

The examples model actions such as:

- navigation
- scrolling
- control activation

The event system evaluates default behavior after listener dispatch.

The conceptual rule is:

`default action executes only when it is enabled and the event has not been cancelled`

The PostgreSQL model stores default actions separately in `default_action`, allowing reporting and policy evaluation without confusing an event with its browser-defined consequences.

---

## Passive Listeners

A passive listener is intended to signal that it will not cancel the associated default action.

The implementations model passive behavior by preserving the original cancellation state when a passive handler attempts to call `preventDefault()`.

This is represented in the examples with a `wheel` event whose scrolling default action remains eligible.

The practical reason for the distinction is performance and predictable input behavior. An event system can treat passive handlers differently because they do not claim control over cancellation.

---

## One-Time Listeners

The `once` option removes a listener after its first successful invocation.

The implementations use this for audit-style behavior.

The lifecycle is:

`registered → invoked → removed`

This is useful for initialization events, one-time setup, or a single interaction that should not remain registered indefinitely.

The examples verify the invariant by dispatching the same event twice and checking that the listener runs only once.

---

## Python Implementation

The Python implementation uses:

- `dataclass` for event and listener state
- `Enum` for event phases
- dictionaries for listener registries
- lists for ordered propagation paths
- sets for element classes
- explicit exceptions for invalid event operations

`Node.dispatch_event()` constructs a root-to-target path and processes capture, target, and bubbling stages.

The implementation also validates tree structure to prevent cyclic parent-child relationships.

The `Listener` structure contains capture, once, passive, and selector properties. This keeps registration state separate from runtime event state.

Assertions verify important behavior:

- a `once` listener executes once
- passive handling does not cancel its default action

The Python program is executable with the standard library only.

---

## JavaScript Implementation

The JavaScript implementation uses Node.js-compatible standard JavaScript.

It emphasizes asynchronous event processing.

Listener callbacks may return Promises, and `dispatchEvent()` awaits them. This models applications where event handling performs asynchronous work while retaining explicit propagation semantics.

The implementation uses:

- classes
- `Map`
- `Set`
- Promises
- async functions
- object-based listener options
- explicit error types

Delegation is implemented through selector matching against the event target and its ancestors.

The implementation also distinguishes a passive listener's cancellation attempt from an actual cancellation of the default action.

The program terminates with a non-zero process status when an event-system invariant fails.

---

## C++17 Implementation

The C++ program presents the event system as an explicit technical engine.

The main domain objects are:

- `Node`
- `Event`
- `Listener`

`std::shared_ptr` and `std::weak_ptr` represent tree ownership and parent relationships.

`std::vector` preserves listener and propagation order.

`std::unordered_map` stores listeners by event type.

`std::unordered_set` stores CSS-like classes.

`std::function` provides listener callbacks without third-party dependencies.

The program uses exceptions for invalid hierarchy construction and invalid event dispatch.

The C++ design makes ownership explicit, which is important when event targets form a mutable hierarchy. Parent links are weak references so that the parent-child ownership graph does not create an unnecessary reference cycle.

---

## Java 17 Implementation

The Java implementation uses an enterprise-oriented domain structure.

Important domain types include:

- `EventTarget`
- `DomainEvent`
- `RegisteredListener`
- `ListenerOptions`
- `InteractionPolicy`
- `EventPhase`

The `ListenerOptions` record provides immutable listener configuration.

`EventPhase` is an enum representing capturing, target, and bubbling stages.

`InteractionPolicy` validates whether an event type is allowed to enter the application event workflow.

The implementation separates:

`event data → listener configuration → propagation engine → policy validation → default action`

This separation makes the model easier to extend with enterprise controls such as permitted event types or security policies.

The program validates:

- event names
- target relationships
- event dispatch ownership
- selector-based delegation
- passive cancellation behavior
- one-time listener execution

## PostgreSQL Data Model

The PostgreSQL implementation models the event system relationally.

The main relationships are:

`event_target`
`→ event_listener`
`→ dispatched_event`
`→ event_delivery`

Supporting policy structures are:

`event_policy`
`→ event_type_policy`

Default actions are represented separately:

`default_action`

The hierarchy itself is represented by a self-referencing foreign key:

`event_target.parent_id → event_target.target_id`

This permits arbitrary nested target structures.

---

## PostgreSQL Propagation Path

The `event_path()` function uses a recursive CTE.

Starting from the target, the query repeatedly follows `parent_id` until the root is reached.

The resulting path is ordered from root to target.

This directly supports the conceptual capture order.

The same hierarchy can then be traversed in reverse to represent bubbling.

The database does not attempt to execute application callback functions. Instead, it records which listeners participate and how dispatch decisions were made.

That separation is deliberate: relational persistence is appropriate for event history, configuration, auditing, and reporting, while runtime callback execution normally belongs to an application process.

---

## PostgreSQL Listener Model

`event_listener` stores:

- target
- event type
- listener kind
- selector
- capture mode
- once behavior
- passive behavior
- enabled state
- execution priority

A delegated listener is identified through `listener_kind = 'delegated'` and a non-empty selector.

A database trigger prevents a listener from being attached to an inactive target.

This demonstrates a database-level integrity rule rather than relying entirely on application validation.

---

## PostgreSQL Event Delivery

`event_delivery` records individual listener deliveries.

It contains:

- event
- listener
- current target
- phase
- sequence number
- prevention state
- propagation state
- execution errors
- delivery timestamp

The sequence number provides an explicit ordering representation.

This makes it possible to report the exact dispatch sequence without reconstructing it solely from application logs.

---

## Transactional Behavior

The SQL script includes a transaction that changes listener state and updates an associated event state atomically.

The principle is:

`BEGIN → listener state change → event state change → COMMIT`

If either operation fails and the transaction is rolled back by the caller, the database does not retain only half of the workflow transition.

This is useful for persisted event-processing state where listener configuration and audit state must remain consistent.

---

## Validation and Failure Conditions

The implementations cover several failure modes.

| Failure or edge case | Handling |
|---|---|
| Empty event type | Validation exception |
| Invalid target | Dispatch exception |
| Cyclic hierarchy | Rejected |
| Non-bubbling event | Bubble phase skipped |
| Cancelled default action | Default action skipped |
| Passive cancellation attempt | Cancellation ignored |
| Once listener | Removed after first invocation |
| Immediate propagation stop | Remaining listeners skipped |
| Delegation selector mismatch | Listener ignored |
| Inactive database target | Listener insertion rejected |
| Excessive hierarchy depth | PostgreSQL policy can reject dispatch |
| Unknown policy event | Policy evaluation denies dispatch |

## Performance Considerations

The event path must be constructed before propagation.

For a hierarchy depth of `h`, path construction is `O(h)`.

If `l` listeners are examined along that path, dispatch is approximately:

`O(h + l)`

Delegated matching can add ancestor traversal for each candidate listener. A broad delegation selector can therefore increase work in large hierarchies.

The database indexes listener lookup by target, event type, capture state, and enabled state.

The PostgreSQL recursive hierarchy query is appropriate for persisted target trees, but extremely deep hierarchies should be constrained by policy.

Listener removal and mutation are implemented carefully so that iteration uses a stable snapshot where necessary.

---

## Security Considerations

Event systems can become security-sensitive when handlers control navigation, authentication state, destructive operations, or privileged UI actions.

The implementations demonstrate several useful controls:

- explicit event-type validation
- separation of propagation control from default cancellation
- delegated selector matching
- passive-listener semantics
- explicit policy validation in Java
- persisted policy evaluation in PostgreSQL
- failure reporting
- prevention of cyclic target structures

A delegated handler should not assume that every bubbled event is trustworthy merely because it originated within an expected container. The actual target and matching selector should be validated before performing sensitive operations.

Stopping propagation is not an authorization mechanism. Authorization must be enforced independently of event delivery.

## Relationship Between the Four Core Concepts

These concepts should not be treated as synonyms.

| Concept | Meaning |
|---|---|
| Event listener | Code registered to respond to an event |
| Capturing | Propagation from ancestor toward target |
| Bubbling | Propagation from target toward ancestors |
| Delegation | Handling descendant events from an ancestor listener |
| `stopPropagation()` | Stops movement to other nodes |
| `stopImmediatePropagation()` | Also prevents later listeners on the current node |
| `preventDefault()` | Cancels cancelable default behavior |
| Passive listener | Listener that does not take control of default cancellation |
| `once` listener | Listener removed after its first invocation |

The core relationship is:

`Event occurs`
`↓`
`Propagation path is determined`
`↓`
`Capture listeners execute`
`↓`
`Target listeners execute`
`↓`
`Bubble listeners execute when applicable`
`↓`
`Default action executes unless cancelled`

Stopping propagation changes the middle of this sequence.

Preventing default changes the final stage.

Delegation changes where application logic is registered, not the underlying propagation mechanism.

## Practical Scenario

The examples use a nested user-interface structure:

`document`
`└── application`
`    └── users`
`        └── user-row`
`            └── delete button`

A click on the delete button can be observed by:

- a document capture listener
- an application capture listener
- the button's target listener
- an application bubble listener
- a document bubble listener
- a delegated users-list listener

A navigation event can be cancelled without stopping propagation.

A wheel event can use a passive listener so the default scrolling behavior remains available.

A one-time audit listener can execute exactly once.

A non-bubbling focus event demonstrates that an ancestor cannot assume all events propagate upward.

---

## Design Boundaries

The implementations intentionally do not claim to reproduce every browser-specific DOM detail.

They model the central mechanics required to understand event propagation:

- target hierarchy
- listener registration
- capture
- target processing
- bubbling
- delegation
- propagation cancellation
- immediate propagation cancellation
- default-action cancellation
- passive listeners
- one-time listeners

A real browser contains additional event types, shadow DOM behavior, composed events, retargeting, browser-specific default actions, pointer-event behavior, and other platform rules.

Those details are outside the scope of this implementation set.

`Event occurrence`
